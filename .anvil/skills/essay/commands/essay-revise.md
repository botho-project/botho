# essay-revise — Reviser

**Role**: reviser (one reviser consumes N critic siblings).
**Reads**: latest `<thread>.{N}/<thread>.md` + `_progress.json` (+ `provenance.md` when the corpus tier is active or the claim ledger has ≥1 `derived` row — issue #1198), `<thread>.{N}.review/` (all files incl. `_gate.json` and `_summary.md.claim_ledger`), the `<thread>.{N}.numeric/` and `<thread>.{N}.hyperlinks/` gate sidecars, resolved `voice:` docs (when the tier is active) + resolved `corpus:` dirs (when that tier is active) + resolved `ai_byline:` (when that tier is active), `<thread>/refs/` + shared `research/`, project `BRIEF.md`.
**Writes**: `<thread>.{N+1}/` with `<thread>.md`, `changelog.md`, `_progress.json` (+ a refreshed `provenance.md`, stamped per step 5b, when either tier is active) — or reports `READY` without writing when the verdict pre-check passes.

## Procedure

1. **Discover state**: find the highest `N` with `<thread>.{N}/<thread>.md`. Require a completed `<thread>.{N}.review/` (else exit pointing at `essay-review`). Require `<thread>.{N+1}/` to not exist (immutability — never revise in place).
2. **Verdict pre-check**: read `<thread>.{N}.review/verdict.md`. When it records `advance: true` AND zero unresolved critical flags, the thread is **`READY` — terminal**: report the publish-handoff summary (resolved body path, total /44, the three handoff guarantees per SKILL.md §Publish handoff contract) and exit WITHOUT writing a new version.
3. **Iteration-cap check**: default `max_iterations: 4` (`<thread>.{max_iterations}/` — `<thread>.4/` at the default — is the worst-case terminal version dir; there is no `<thread>.5/` under a default cap); project-BRIEF paired override (`max_iterations` + `iteration_cap_rationale`) per the #349 memo contract — the BLOCKED notice surfaces the rationale verbatim when an elevated cap is hit. At cap → report `BLOCKED — human review required` and exit.
4. **Read all critic input**: `verdict.md` (top revision priorities first), `scoring.md` (per-dim deductions), `comments.md` (severity + `scope` tags, plus any `Downstream risk:` line per finding — issue #1197, `essay-review` step 6c), `_gate.json` + the `.numeric/` and `.hyperlinks/` `_review.json` payloads (the mechanical findings carry exact lines and suggested fixes), and the "What's working" list.
5. **Load voice grounding (conditional)**: when the project BRIEF declares a `voice:` block, resolve the docs and read them alongside the critic feedback. **Preserve the voice signatures the reviewer flagged as working** — voice-grounded revision must not sand off the persona while chasing rubric points (`anvil/lib/snippets/voice_grounding.md` §Reviser contract). When the review carried the missing-voice-contract `major` finding, surface it in the report (the fix is operator-side BRIEF authoring, not body editing).
   - **Subject voice tier (conditional — issue #598)**: when the BRIEF declares `voice.subjects`, also resolve them via `anvil/lib/project_brief/voice.py::resolve_subject_voice_docs(<project_dir>)` and read each speaker's transcript corpus (+ `voice_doc`) alongside the critic feedback. **The one-line preservation rule extends to subject voices**: preserve the subject voice signatures the reviewer flagged as working — a reconstructed line marked corpus-faithful must not be sanded into model polish while chasing rubric points (`voice_grounding.md` §"Subject voice tier" → Reviser contract). When a **Misattribution** critical flag (8) was raised, addressing it usually means re-voicing the line into the correct speaker's cadence (or moving it to the right speaker's mouth) — not deleting the dialogue; like every critical flag it MUST be addressed, never `declined`.
5a. **Corpus provenance tier (conditional — issue #611)**: when the BRIEF declares a top-level `corpus:` (i.e., `anvil/lib/project_brief/voice.py::resolve_corpus_dirs(<project_dir>)` returns ≥1 dir), read the `<thread>.{N}/provenance.md` claim→source map alongside the critic feedback. **Copy it forward**: write a refreshed `<thread>.{N+1}/provenance.md` applying the same updates as the prose revision — new claims added in the revision get new rows (each with an `Anchor`, per `anvil/lib/snippets/provenance.md` §Section 2, issue #868, and `Kind: corpus`, issue #1198); claims removed drop their rows; changed claims have their `Source file` / `Line range` / `Anchor` updated to match the revised prose **and their `Verified against`/`Verified at` cells cleared** (a changed claim is unverified again until the next review checks it — see step 5b). Any fabrication-class critical flag (9–13) MUST be addressed — cut the fabricated claim or re-ground it in a real corpus passage, never invent a citation. Per `anvil/lib/snippets/provenance.md` §Section 2 reviser discipline, the map stays in sync with the body through every pass. **Mechanically repoint drifted anchors (§Section 4b, #868)**: after copying the map forward, run `python -m anvil.lib.provenance_anchor repoint <thread>.{N+1}/provenance.md <corpus_root> [...]` — it rewrites only the `Line range` cell of rows the back-check's anchor-drift pre-check (step 4c of `essay-review`) flagged `DRIFTED`, leaving every other cell (including every `derived`-kind row, which the tool never recognizes as a corpus citation — see step 5b) untouched; this is mechanical, never the fabrication case above. Carry forward `metadata.corpus_dirs_resolved` in the new `_progress.json`. When the tier is inactive (no `corpus:` key), skip the `Kind: corpus` half of this step entirely — no corpus-row copy-forward, **byte-identical to pre-#611** — but step 5b below still runs if `derived` rows exist.
5b. **Claim ledger — copy forward, clear on change, stamp verified rows (issue #1198)**: this step runs whenever `<thread>.{N}/provenance.md` exists with ≥1 row of either `Kind` — a SUPERSET of step 5a's corpus-tier activation, covering `Kind: derived` rows (a count/fact from `<thread>/refs/`, shared `research/`, or a linked repo — see `essay-draft.md` step 4b) the same way regardless of whether `corpus:` is declared.
   - **Copy every row forward unless the revision changed it**: a `derived` row whose `Claim` text and `Source file` reference are untouched by this revision keeps its `Verified against`/`Verified at` exactly as `essay-review` left them — this is the entire point of the ledger (a claim checked once stays checked until something about it actually changes, closing #888's "effort went to re-verifying what was already verified"). A row whose `Claim` text changed, or whose evidentiary reference changed, has its `Verified against`/`Verified at` cells CLEARED (blank) — it is unverified again until the next `essay-review` pass checks it; do NOT carry a stale stamp forward onto changed content.
   - **Stamp the rows the just-completed review checked clean**: read `<thread>.{N}.review/_summary.md.claim_ledger.checked_clean_lines` (written by `essay-review` step 4d) and, in `<thread>.{N+1}/provenance.md`, run `python -m anvil.skills.essay.lib.claim_ledger mark-verified <thread>.{N+1}/provenance.md --lines <L1,L2,...> --against "essay-review v<N>" --at <N>` (prefix `uv run --project .anvil` in an installed consumer repo) — note the line numbers refer to the row's position in the JUST-COPIED `<thread>.{N+1}/provenance.md`, which is byte-position-identical to `<thread>.{N}/provenance.md` for every unchanged row, so the review's line numbers still resolve correctly as long as no row ABOVE a stamped one was added or removed during this same revision; if rows were reordered/inserted above a to-be-stamped row, re-resolve its new line number by matching on `Claim` text before stamping (the CLI stamps by line number, never by claim-text search, so this re-resolution is the reviser's job, not the tool's). A row this pass's revision changed is NEVER in `checked_clean_lines` (the review that produced it ran against the PRIOR version's text) — it stays unverified per the bullet above regardless.
   - **Never fabricate a stamp.** `mark_verified` only records that a check happened — it never substitutes for one. Do not call it on a row that was not actually in `checked_clean_lines`, even if the revision "obviously" didn't touch it — the review's own record is the source of truth for what was checked this pass, not the reviser's assumption.
   - **When inactive** (no `provenance.md`, or zero rows after the corpus-tier's own copy-forward): skip entirely — no ledger, no stamping, byte-identical to having nothing to track.
5c. **AI-authorship byline (conditional, opt-in — issue #941)**: re-invoke `anvil/lib/project_brief/voice.py::resolve_ai_byline(<project_dir>)` — re-resolved fresh each pass (a rendering step, not carried content, so a mid-thread BRIEF edit — a new `text:` override, a changed `placement:`, or the tier being enabled/disabled) takes effect on the very next revision without special-casing). **When active**: apply the drafter's step-5 byline insertion rule (`essay-draft.md` step 5) to `<thread>.{N+1}/<thread>.md` — this both refreshes an existing line to any changed config and adds one that was newly enabled since the prior version. Record `metadata.ai_byline_text` / `metadata.ai_byline_placement` in the new `_progress.json` (mirrors the drafter). **When inactive**: omit both keys and ensure no byline line is present (strip one forward if the tier was disabled since the prior version — never leave a stale disclosure line the BRIEF no longer declares).
6. **Build the revision plan**, ordered: (1) critical flags — every flag MUST be addressed (an example-coherence flag usually means reframing or replacing the example, not polishing the prose around it; a numeric flag means fixing the arithmetic or naming the bridging number, not deleting all numbers); (2) blocking gate findings (broken links: fix the target or remove the dependent claim); (3) `blocker`/`major` comments; (4) the lowest-scoring dims' deductions, honoring `scope: reduce` items — at this length, cutting is usually the highest-leverage edit; (5) `minor`/`nit` only when they don't conflict with (1)–(4). Never touch the "What's working" list.

   **Downstream-risk consequence, addressed in the SAME pass (issue #1197)**: when a finding being addressed at (1)–(5) carries a `Downstream risk:` annotation, the plan item for that finding is NOT just the literal `suggested_fix` — it is the fix PLUS the named consequence, folded into one edit:
   - **`cross-reference-dangle`**: before or immediately after applying the fix, open the named referring location and repair it in the same pass (re-align the cross-referenced number/claim, update the phrase that pointed at the old text, or remove the reference if it no longer applies). Do not leave the referent dangling for the next `essay-review` cycle to catch — that is exactly the failure mode #1197 exists to close (`wave-one-bandgaps` `.2`→`.3`).
   - **`envelope-breach`**: apply the fix, then check the resulting word count (`python -m anvil.lib.word_count <body>`, the canonical method — #1349) against the declared ceiling (BRIEF `target_length`, or the default 500–1500 word envelope). If the fix pushed the body over, make the compensating cut named by the annotation (or, absent a named candidate, the highest-leverage `scope: reduce` item already in the plan) as part of THIS pass, not a follow-up revision.
   - **Any other named consequence**: address it the same way — the fix and its foreseeable knock-on effect land in the same version, together.
   - A finding with no `Downstream risk:` annotation is unaffected — apply its `suggested_fix` as usual.
7. **Write `<thread>.{N+1}/<thread>.md`** (slug-echo per #295) applying the plan. Re-run the drafter's step-5 self-disciplines on the result (numeric re-derivation, example-needs-the-gate check, register, close) — the revision must not introduce a fresh instance of the failure mode it just fixed.
8. **Write `changelog.md`** mapping each consumed critic note to the change made (or to an explicit `declined — <reason>` entry; deductions may be argued against, critical flags may not). When a finding carried a `Downstream risk:` annotation, the changelog entry names BOTH the fix and how the named consequence was handled (e.g. "Fixed §3's stale 40% figure; also re-aligned §1's cross-reference to the same number per the noted downstream risk") — a bare "fixed" entry that is silent on an annotated consequence is incomplete.
9. **Initialize `_progress.json`** for the new version: `phases.revise.state = done` (LAST write), carry forward `metadata.voice_exemplars`, — when the subject tier is active — `metadata.subject_voice_exemplars` (the per-subject transcript map; both updated if different exemplars were consulted), — when the corpus tier is active — `metadata.corpus_dirs_resolved` (issue #611), — when the claim ledger has ≥1 row — `metadata.claim_ledger_summary` (`anvil.skills.essay.lib.claim_ledger::summarize` over the just-written `<thread>.{N+1}/provenance.md`, issue #1198), — when the AI-byline tier is active — `metadata.ai_byline_text` / `metadata.ai_byline_placement` (issue #941, re-resolved by step 5c, not blindly copied), and **append the `score_history` row** for the completed review iteration per `anvil/lib/snippets/progress.md` §Convergence fields: `{ "iteration": <N>, "total": <reviewed-total>, "threshold": 35, "rubric_id": "anvil-essay-v1" }`. Stable-score termination (`STALLED`) follows `anvil/lib/snippets/rubric.md` §"Termination resolution order" over this history — the claim ledger changes what a review pass covers, never this resolution order (see `anvil/skills/essay/lib/claim_ledger.py`'s module docstring §"Composition with `anvil/lib/critics.py` / `anvil/lib/convergence.py`").
10. **Report**: e.g., `Revised the-loop-is-the-unit.1 → the-loop-is-the-unit.2 (addressed 1 critical flag, 4 major comments; 2 declined with reasons). Next: essay-review the-loop-is-the-unit`.

## What essay-revise does NOT do

- **Never edits `<thread>.{N}/` or any critic sibling in place** — immutability is the audit trail.
- **Never advances state itself** — the next `essay-review` pass scores `<thread>.{N+1}/` on its own merits; there is no "the reviser fixed it" credit.
- **Never bypasses critical flags** — a changelog `declined` entry is legitimate for scoring deductions, never for flags or broken links.
- **Never sands off the persona** — rubric-point chasing that flattens flagged-as-working voice signatures is the named meta-failure mode.
- **Never stamps a claim-ledger row `Verified against`/`Verified at` that is not in the just-completed review's `checked_clean_lines`** (issue #1198) — the reviser mechanically records what `essay-review` already checked; it never performs or infers a verification itself.

## Git sync (opt-in, off by default)

Per `anvil/lib/snippets/git_sync.md` (`.anvil/anvil/lib/snippets/git_sync.md` in an installed consumer repo): if `.anvil/config.json` exists and `git.commit_per_phase` is `true`, end this phase: stage only the dirs this phase wrote, commit as `anvil(<skill>/<phase>): <thread>.{N} [<state>]`, push if `git.push` is `true`. Git failures warn and continue — never fail the phase. When the config or knob is absent, skip this step entirely (default off).

This phase's specifics:

- **Ordering**: after the `_progress.json` `done` write lands. On the no-write paths (READY / BLOCKED at step 2–3) there is nothing to commit and the hook is a silent no-op.
- **Staging target**: ONLY this command's own `<thread>.{N+1}/` version dir.
- **Commit**: `anvil(essay/revise): <thread>.{N+1} [REVISED]`.
